# Loops and Models

<!-- point: two-ideas-loop-and-model | Two ideas carry the rest of the book: all agent work is a loop, and an agent steers that loop well only when handed a model of the world it works in — engineering the loop and handing over the model, deliberately and every time, is the MAGE method. -->
Two ideas carry the rest of this book, and everything else is a consequence of them.
The first is that all agent work is a *loop*. The second is that an agent steers that
loop well only when you hand it a *model* of the world it is working in. This is what
makes the MAGE method work: Model-Based Agentic Software Engineering means engineering that
loop and handing the agent that model, deliberately, every time. Get these two
right and the agent finds your answer fast; get them wrong and it wanders. Let me take
them in turn.

## Everything is a loop

<!-- point: agent-work-is-a-fixed-shape-loop | An agent runs in a loop of fixed shape — input (the problem plus a notion of success), reasoning, action, output, folded back into the next input — and shaping that loop is loop engineering, of which nearly everything in the book is an instance. -->
<!-- index-def: loop-engineering -->
An agent does not run in a straight line — it runs in a loop, and the loop has a fixed
shape. It takes an input: the current problem, plus some notion of what success looks
like. It reasons, and it acts in its operating environment. It produces a result. And
that result folds back into the input for the next turn. Input, reasoning, output,
fed around again. Shaping that loop is **commonly called loop engineering**, and
nearly everything in this book is an instance of it. [ref:the-loop] draws its fixed shape.

<!-- label: the-loop -->
<!-- figure: assets/loop-engineering.svg | The loop that is the unit of agent work. The success metric is drawn in the accent color because defining it is the hard question. -->

<!-- point: loop-starts-with-a-measurable-metric | Engineering a loop well starts with the metric, because the agent steers by it and does not know your goals; make progress measurable — deterministically, by a quantitative check, or by a rubric scoring a qualitative result — or the agent searches forever, never knowing when to stop. -->
<!-- index-def: success-metric -->
Engineering a loop well starts with the metric, because the metric is what the agent
steers by. The agent does not magically know your goals or your environment. You have
to make its progress *measurable* — deterministically, through a quantitative check,
or through a rubric that scores a qualitative result. Skip this, and you have told the
agent nothing about what "done" means, so it searches, and searches, and searches, and
never knows when to stop.

<!-- point: orchestrator-is-a-worked-loop-written-as-a-model | The companion repository's orchestrator is a worked example of an engineered loop: it models the dispatch → work → land → tombstone lifecycle as an explicit reactive loop written down as a model the agent can read, rather than left implicit in the code — which is exactly the second idea. -->
<!-- index-example: loop-engineering -->
The orchestration layer of this book's companion repository is itself a worked example
of a loop engineered this way. The catalogue models the orchestrator — the process
that dispatches agents, waits for them to land work, and cleans up after them — as an
explicit reactive loop with a typed lifecycle: *dispatch → work → land → tombstone*,
then refill and go again. The loop is not left implicit in the code; it is written
down as a model the agent can read, which is exactly the second idea.

> Learn more about this governance mechanism: [orchestrator model](appendix-b-agent-orchestration-model.html).

## Give it a model of the world

<!-- point: vibe-coding-io-device-vs-engineering-system | Vibe coding treats the program as an I/O device; engineering treats it as a system. -->
> Vibe coding treats the program as an I/O device; engineering treats it as a system.

<!-- point: io-vs-system-is-what-counts-as-proof | The difference between the two is not aesthetic but what counts as proof a change is good: the I/O device asks only whether the right thing came out this time, the system asks what must stay true across every input — and the fast, seductive I/O default is what turns a hundred thousand lines into a mess nobody can reason over. -->
The difference is not aesthetic. It is what counts as proof that a change is good. Treat the
program as an I/O device and the only question is whether the right thing came out this time.
Treat it as a system and you ask what must stay true across every input, and you build the
structure that holds the answer. Agents make both modes cheap, which is why you have to choose
deliberately. The fast, seductive default is the I/O device, and the I/O device is what turns
a hundred thousand lines into a mess nobody can reason over.

<!-- point: model-of-the-world-is-the-input-agent-reasons-over | The second piece is the model the agent reasons over: a sense of the environment — what happens when it pulls a lever, and what it is even allowed to do — which is itself an input, and supplying it tells the agent what kind of reasoning the situation calls for. -->
The second piece is the input the agent reasons *over*. You have to give it a sense of
the environment: when it pulls this lever, what happens, and what is it even allowed to
do? That sense of the world is itself an input, and when you supply it, the agent knows
what kind of reasoning the situation calls for.

<!-- point: model-is-a-probabilistic-reasoning-machine | Writing the model down is not wasted breath because a foundation model is a probabilistic reasoning machine: probabilistic means it does not always do exactly what you want, reasoning machine means it genuinely reasons over real internal structure — so it reads what you write and reasons over it. -->
<!-- index-def: probabilistic-reasoning-machine -->
It is worth being blunt about why this works, because it is easy to feel like you are
writing documentation into a void. A foundation model is, loosely, a probabilistic
reasoning machine. *Probabilistic* means it does not always do exactly what you want.
*Reasoning machine* means it genuinely reasons — the interpretability work probing these
networks keeps turning up real internal structure, and even lets us steer it. [The Agent
Stack](2.1-the-agent-stack.html) makes that case in full. So writing the model down is
not wasted breath. It reads it, and it reasons over it.

<!-- point: agent-behavior-is-a-search-over-a-vast-space | The most useful way to hold this is as a search: the agent is searching an enormous space — every place the answer might live, every configuration, every function that might implement the ask — far too large to sweep. -->
<!-- index-def: search-space -->
The most useful way to hold this is as a search. The agent is searching an enormous
space: every place the answer might live, every configuration it might try, every
function that might implement what you asked. That space is far too large to sweep.

<!-- point: structuring-loop-and-model-conditions-the-distribution | Structuring the loop and handing over a model conditions the probability distribution of the agent's behavior — biasing its search toward where the answer actually is; done well this moves the agent from failing the task to completing it, and completes already-solvable tasks in fewer tokens and less time. -->
So when you structure the loop and hand over a model, what you are really doing is
**conditioning the probability distribution of the agent's behavior** — biasing it to
search where the answer actually is. Done well, this takes the agent from failing your
task to completing it. And when it was already completing the task, it now does so in
fewer tokens and less time, so you get back to the interesting parts of your job.

<!-- point: a-model-aims-the-search-and-shrinks-what-is-held | A model earns its keep twice: it aims the search, and it shrinks what the agent must hold — which keeps the work from spilling the context window and churning. -->
A model earns its keep twice over here. It aims the search, and it shrinks what the
agent has to hold — which is what keeps the work from spilling the window and churning.

<!-- point: the-printers-seam-is-determinism-vs-probability | The printer metaphor's honest break: a real 3D printer is deterministic — same G-code, same part — while this printer is probabilistic — the same prompt can yield different output — which is why we condition the agent's distribution rather than merely instruct it; the metaphor claims you get only what you describe, not that you get the identical thing twice. -->
> **The metaphor's seam.** Lakoff and Johnson, in *Metaphors We Live By* (1980), show that
> a structural metaphor illuminates where its source and target align and misleads where they
> break, so naming the break is part of honest use. Here is ours: a real 3D printer is
> deterministic — the same G-code yields the same part, every run. This printer is
> probabilistic — the same prompt can yield different output. That is exactly the gap the
> chapter turns on. Because the agent is a probabilistic search and not a deterministic
> extruder, we condition its distribution rather than merely instruct it. The metaphor claims
> "you get only what you describe"; it does not claim "you get the identical thing twice."
