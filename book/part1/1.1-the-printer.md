# The Printer

## What this book is about (and what it is not)

<!-- point: task-mode-is-first-judgment | The first judgment an agentic engineer makes is whether a task needs governed autonomy at all, because some tasks a capable model completes in one pass. -->
Not every programming task needs the machinery this book describes. Some tasks can simply be done directly by a
capable model. You describe the input and the output, you push the button,
and a working program comes back on the first pass. There is no need for iteration, nor governance, nor loop management.
Knowing which tasks are like that, and
which are not, is the first judgment an agentic engineer has to make. [ref:task-mode-decision]
lays out that judgment as a flowchart.

<!-- label: task-mode-decision -->
<!-- figure: assets/one-shot-vs-supervised-autonomy.svg | Two modes of coding agent use. From "What kind of task", you specify the input/output behavior, then split on (your estimate of) size and difficulty. A simple task with no reasoning goes to one-shot scripting: describe the process, get it back in a single pass. A hard task, especially one that includes reasoning, goes to supervised autonomy, where you supply correctness conditions and proposed sub-tasks to shape the system, plus tools that determinize recurring processes and monitoring-and-intervention to shape the development process. If you're not sure, try to one-shot it. But if the one-shot effort doesn't pan out, don't throw good tokens after bad. Just switch over to the other path. -->

### The two modes

<!-- point: two-modes-fork-on-size-and-difficulty | Once a task's input and output are stated, the choice of mode forks on the work's size and difficulty. -->
Start at the decision on the left. You have a computational task and you can say
what it takes in and what it must produce. From there the path forks on how big
and how hard the work is.

<!-- point: one-shot-for-small-unsubtle-tasks | One-shot scripting fits a small task that needs no subtle reasoning: specify the behavior once, take the single-pass result, skip the governance apparatus. -->
**One-shot scripting** is the righthand branch. The task is small, a few thousand
lines at most, and it does not ask the agent to reason its way through anything
subtle. A CSV-to-HTML report script is the shape of it. You specify the behavior
once, the agent writes it in a single pass, and you read the result. The whole
transaction fits in one context window and one sitting. When a task really is this
size, reaching for the full apparatus of governed autonomy is wasted effort. Send
it one-shot and move on.

<!-- point: supervised-autonomy-supplies-four-things | Supervised autonomy fits a hard or oversized task: rather than hand the agent the whole job, you supply four things — correctness conditions, sub-tasks, determinizing tools, and monitoring-and-intervention — in two groups, one shaping what gets built and one shaping how the building runs. -->
**Supervised autonomy** is the downward branch, and it is where most of this book
lives. The task is hard, especially if it includes reasoning, and it is too large
to hold in a single context window or to trust to a single pass. So you do not hand
the agent the whole job and hope. You supply four things, in two groups. The system
side shapes what gets built:

- **Correctness conditions** — what a right answer looks like.
- **Sub-tasks** — the breakdown you have proposed to divide the work.

The development side shapes how the building runs:

- **Tools that determinize recurring processes**, so the same operation runs the
  same way every time.
- **Monitoring and intervention**, so you can watch the work and step in when it
  drifts.

<!-- point: book-structure-fills-the-four | The four elements form the skeleton of supervised autonomy, and each later part of the book develops one of them. -->
Those four are the skeleton of supervised autonomy, and each later part of the book
fills one of them out.

### Where the emphasis falls

<!-- point: mode-misjudgment-is-costly-both-ways | Telling the two modes apart is the first skill, and misjudging it either way is expensive: over-govern a one-shot task and you drown it in ceremony; under-govern a supervised one and you get plausible, subtly wrong output at unreadable scale. -->
This book is about both modes. It has to be, because the first skill is telling
them apart, and getting that wrong in either direction is expensive. Treat a
one-shot task as if it needed supervised autonomy and you drown a five-minute
script in ceremony. Treat a supervised-autonomy task as if it were one-shot and you
get confident, plausible, subtly wrong output at a scale no human can read.

<!-- point: leash-length-from-data-density-and-capability | How long a leash a task can run on depends on two things: how densely the model's training data covers the work, and how capable the model is at it — well-trodden work for a strong model can be described briefly and trusted far, edge work needs the reasoning broken into smaller checked steps. -->
So the book spends real pages on the sizing question. How long a leash a task can
run on comes down to two things: how densely the model's training data covers the
kind of work you are asking for, and how capable the model is at that work in the
first place. A task that sits in well-trodden territory for a strong model can be
described briefly and trusted far. A task at the edge of what the model has seen
needs the reasoning broken into smaller, checked steps. Judging that distance is
what tells you whether a job can go one-shot or has to be supervised, and the book
gives you the means to judge it.

<!-- point: books-weight-is-supervised-autonomy | The book's weight falls on supervised autonomy — building products whose quality needs exceed what a model can be trusted to do alone and whose size exceeds any context window — because that is the new, unwritten engineering. -->
But the weight of the book is on the downward branch. The interesting engineering, the
part that did not exist a few years ago and is not yet written down, is
**supervised autonomy**: building larger-scale products whose quality needs exceed
what a model can be trusted to do alone, and whose size exceeds current and
foreseeable context windows. That is the regime where you stop pressing go on a
script and start running a printer, framing the goal, modeling the world for the
machine, and putting every change on rails from dispatch to production. Everything
after this chapter is about how to do that well.

<!-- point: code-is-cheap-now-productionize-it | Writing code is no longer the expensive part, so the book's premise is turning a fast code-fabricator into a production line. -->
Writing code used to be the expensive part. It no longer is. So the premise of the
book is short: we've got a fast code-fabricator and we need to figure out how to
turn that into a production line.

## The printer

<!-- point: printer-is-the-governing-metaphor | A 3D printer builds almost anything from spooled filament, limited only by material and imagination; it is the governing metaphor of the book because coding with an agent is far more like running a printer than people expect — and that difference is the difference between blaming the tool and blaming yourself. -->
<!-- index-def: printer-metaphor -->
A 3D printer will build almost anything you can imagine — a replacement gear, a
prosthetic hand, a scale model of a building — out of nothing but spooled filament.
Its only hard limits are the material and your own creativity. That machine is the
metaphor that drives this entire book, because building software with a coding agent
is far more like running a 3D printer than most people expect. And the difference
between the two is the difference between blaming the tool and blaming yourself.

## An open-ended technology

<!-- point: open-ended-technology-mints-genres | A 3D printer is an open-ended technology, in the rare company of writing and the printing press: none arrives with a list of what to make, so people must invent the genres, and cheap production mints genres no predecessor could justify. -->
A 3D printer is not just a machine. It is an *open-ended* technology, and that puts it in rare
company — with the invention of writing, and with the printing press. What those three share is
that none of them arrives with a list of what to make. People had to invent that. Writing began
as marks for counting cattle; only later did someone find you could write a poem, and later still
that a poem could rhyme, could take a stanza, could hold a shape — and then the textbook, the
treaty, the contract. Each was a *genre* somebody had to work out. The printing press inherited
every genre writing had found, and then, by making production cheap, minted ones no scribe could
ever have justified: the poster, the pamphlet, the newspaper.

<!-- point: genai-is-open-ended-book-takes-one-genre | Generative AI is open-ended the same way, so the work is not only to run the machine but to work out which genres are worth producing and a method for each; this book takes one genre — production software, code whose named quality metrics each change traces back to. -->
Generative AI belongs to this class. It is open-ended in the same way — it will make almost
anything, and it hands you no list. So the work is not only to run the machine. It is to work out
which genres are worth producing, and the method for producing each one well. This book takes one
genre and gives it a method: **production software** — code whose quality metrics you actually
care about, and whose every change you can trace back to the metric it moves.

<!-- gloss: Quality metrics | The properties of the code you actually care about — correctness, performance, security, maintainability — named explicitly, and traceable: for any change, you can point to the metric it moves. Production software is code whose quality metrics are named and whose changes map back to them. -->

<!-- point: quality-floor-was-always-the-price-now-cheap | The book's apparatus is not decoration but the price of any trustworthy software — name the properties that must hold, check them, tie every change to the property it moves; that price was always the same, and what changed is that agents drop its cost so the assurance once affordable only to a regulated few is now within nearly anyone's reach. -->
> **The quality floor, made cheap.** None of the apparatus in this book — the
> models, the gates, the traceability — is optional decoration. It is the price of
> *any* software you can trust: name the properties that must hold, check them, and
> keep every change tied to the property it moves. That price was always the same. What
> changed is who can afford it. For decades this level of assurance was reachable only by
> the shops that could justify the cost — the Rolls-Royces and the Boeings, where a
> mistake is catastrophic and a modeling program pays for itself. Agents drop that cost
> to almost nothing: they write the checks, maintain the models, and hold the line, so
> the quality once affordable only to a regulated few is now within reach of almost
> anyone. The method teaches how to get very high quality nearly for free. [data: nearly-free]

## A picture is not enough

<!-- point: everyone-can-sketch-software-but-a-picture-wont-print | Anyone can picture a piece of software, because the concept is easy to picture — but a picture is not a thing you can print. -->
Everyone can sketch a piece of software. We have all used Google Maps, spreadsheets,
a document editor — programs that take in data and do something useful with it. The
concept is easy to picture. But a picture is not a thing you can print.

<!-- point: printer-needs-a-model-not-a-photo | A 3D printer given a photograph produces nothing; it needs a model of internal structure plus print notes, because there are a hundred ways to misprint a part that looked fine as a picture. -->
<!-- index-def: picture-vs-model -->
Hand a 3D printer a photograph of the object you want and nothing comes out. The
printer needs instructions: a CAD model that shows not just the outer shape but the
internal structure — how the pieces fit, where the load is carried — and then a set
of print notes on top of that. You slice the model into layers, and you think about
how those layers compose as the machine lays them down. Different materials have
different minimum thicknesses, different strengths, different joints that hold and
joints that fail. There are a hundred ways to misprint a part that looked fine as a
picture.

<!-- point: agents-need-the-instructions-not-just-the-picture | Software agents are the same: you cannot hand an agent only the picture of what you want; you must supply the detailed build instructions, and the quality of the result tracks the quality of those instructions. -->
<!-- index-example: picture-vs-model -->
Software agents are the same. You cannot hand an agent only the picture of what you
want. You must also give it — or work out how to give it — the detailed instructions
for how to build it. Good instructions, and it works beautifully. Bad instructions,
and you have not got a hope.

## Whose fault is it?

<!-- point: agent-is-a-printer-not-a-stapler-so-suspect-the-instructions | The posture the book turns on: an agent is not a foolproof stapler but a printer that builds only what its instructions describe, so when it produces the wrong thing the first suspect is the instructions, not the model. -->
<!-- index-def: whose-fault -->
Here is the shift in posture the whole book turns on. When you use a stapler and the
staple jams, that is the stapler's fault, not yours. A stapler is supposed to just
work — it is so foolproof my three-year-old runs one, insert the paper, ka-chunk, no
problem. That is exactly what an agent is not. An agent is not a stapler — it is a
printer, and a printer only ever builds what its instructions describe. So when the agent produces the wrong thing, the first
suspect is not the model. It is the instructions.

<!-- point: models-can-build-anything-you-can-explain | In the author's experience every agent failure traced back to his own instructions: state-of-the-art models can build essentially anything one can envision so long as you can explain it, and that "so long as" is the whole job — a real, teachable engineering discipline. -->
<!-- index-example: whose-fault -->
In my own experience, every single time an agent has failed to produce what I wanted,
it turned out to be my fault. The state-of-the-art models can build essentially
anything we can envision in software, as far as I can tell — *so long as you can
explain it to them*. That "so long as" is the entire job, and it is a real engineering
discipline, not a knack. This book teaches it. And the discipline is older than it
looks: an engineer has always been accountable for the instructions handed to a machine,
even the ones not hand-crafted — the back matter returns to what that responsibility
becomes when the thing you author is the model, not the code.

<!-- point: the-promise-is-also-the-danger | That the printer builds anything you describe is both the promise and the danger: with no judgment behind it, it builds a wrong thing as fast and willingly as a right one, carrying you at full speed exactly where your instructions point. -->
The printer builds anything you can describe. That is the promise, and it is real. It is
also the danger, because a printer with no judgment behind it builds a wrong thing as fast
and as willingly as a right one, and carries you at full speed exactly where your
instructions point.

> Claude is the fastest road to hell.

<!-- point: speed-exposes-the-danger-not-causes-it | Speed is not the danger but exposes it: hand the machine a doomed idea and it does not slow to warn you, it builds your mistake with the same tireless fidelity as your success, and which one comes out is the instructions, which are yours. -->
The speed is not the danger. The speed *exposes* the danger. Hand the machine a doomed idea
and it does not slow down to warn you; it makes the doomed idea better and better, an
afternoon's ten thousand plausible lines deep into a circle you chose yourself. The printer
that builds anything will build your mistake with the same tireless fidelity it builds your
success. Which one comes out is the instructions, and the instructions are yours.

<!-- point: running-example-is-a-real-shipped-system | The book's running example is not a toy but a real shipped system — DocAble, the production accessibility-remediation tool — returned to in every later chapter so what the reader watches getting printed correctly is a system that actually shipped. -->
A word on the example this book builds on. I do not reach for a toy. The running system
is the real one: DocAble, the production accessibility-remediation tool — its own pipeline,
its own agent fleet, its own scars — described in full at the back, in
[The Built System](5.3-the-built-system.html). Every later chapter returns to it, so what you watch getting printed
correctly, chapter by chapter, from model through mechanism and architecture to migration,
is a system that actually shipped, not a demo staged to make the argument come out clean.
