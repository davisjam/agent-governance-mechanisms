Review the book's argument as ~10–20 statements. Draft (author's starting set):
1. Coding agents make implementation abundant but unreliable.
2. Human per-change oversight does not scale with agent throughput.
3. Large agentic projects decay into churn when intent, architecture, and invariants do not fit or remain visible.

5. Enforced governance mechanisms keep implementation aligned with intent.
6. Failures at velocity reveal missing structural controls.

### Task 3 — Truncate the appendix (the catalogue) by an editorial rubric
Include every catalogue entry that is genuinely innovative, illuminating, and durable enough to improve the reader's model of agentic software engineering. Exclude entries that merely document local machinery, repeat a broader pattern, or are likely to age into implementation trivia. (Exclusion ≠ deletion from the book — it can remain as a worked example, sidebar, known-use, variant, or implementation note, or live in the complete ONLINE catalogue.)

**INCLUSION criteria (an entry earns PRINT if it clears these — a durable idea worth carrying into the reader's next system):**
1. **A non-obvious engineering idea** — beyond "write tests / use CI / document architecture / serialize a shared resource / wrap an API." Ordinary practices qualify only when the entry adds a genuinely novel mechanism/synthesis (Mediator + single-writer contracts > "use a wrapper" because permitted seams are declared in a model and a coverage lint detects every bypass). Test: *would a strong senior engineer plausibly say "I had not thought of doing it that way"?*
2. **Reveals something distinctive about engineering WITH AGENTS** — an old technique can qualify by becoming newly important / changing form / composing differently under agentic velocity (blocking lints aren't new, but: agents produce violations too fast for human review → machine enforcement → right semantic level → scoped reason-bearing suppressions → durable infra not reviewer memory). Novelty can reside in the agentic adaptation, not the primitive.
3. **Instantiates a central thesis** — Modeling (structured models let agents reason over a compact coherent representation) or Alignment (enforced mechanisms keep implementation aligned with intent). The two theses are what keep the book from being "a list of tricks." (Executable source-of-truth models → Modeling; drift/parity gates → modeling→enforcement; closed action vocabulary → constrains probabilistic reasoning via deterministic surfaces; trust-nothing completion gates → replace self-report with re-derived evidence.)
4. **Changes the architecture of the engineering PROCESS** — moves policy from human memory → enforced gate; architecture from prose → executable model; completion from assertion → recomputed evidence; mutation from arbitrary paths → closed vocabulary; testing from line-coverage → explicit model obligations; provenance from logs → a trace carried with the change. Not local optimizations — they change the shape of the system/process.
5. **Generalizes beyond DocAble** — the mechanism has a plausible transferable abstraction (PdfModel is specific; "one sanctioned mutation surface, protected by a ban-lint" is general. a11y_ prefixes are local; "durable attribution attached at the mutation point + checked for complete wiring" is general). Test: *can the pattern be described without mentioning PDF, accessibility, Claude, or the repo — and remain interesting?*
6. **Durable value even if models improve** — addresses a problem better reasoning alone doesn't eliminate. Durable: explicit system intent · bounded authority · independently-checked completion · provenance · model–implementation reconciliation · semantic preservation · concurrency invariants · architectural boundaries · assurance coverage · control interaction. Vulnerable to model progress: reminders for forgetfulness · repeated context reinjection · pre-compaction summaries · prompt-format tricks · token-count-loss compensations · today's-capability-gap model-tier routing. Test: *does the engineering OBLIGATION survive even if the implementation mechanism changes?* (Print preserves the obligation + durable pattern; leave transient implementation online.)
7. **Meaningful forces and tradeoffs** — not "do the good thing." Explains: what failure recurs · why the obvious fix is inadequate · competing forces · what it guarantees · what it costs · where it fails · what new risks it introduces. (Closed action vocabulary improves auditability/boundedness but may constrain novelty, require vocabulary expansion, pressure unsafe escape hatches, over-centralize authority.)
8. **Composes with other mechanisms** — the strong compositions are part of the value (sole mutation seam → complete provenance feasible → wiring-lint enforces coverage → stamps support derived changelog → content-preservation validator catches damage through the sanctioned seam). Earns inclusion when it reveals a strong composition.
9. **Backed by a compelling failure/success story (scars)** — what went wrong · why existing controls failed · what mechanism you introduced · what class of failure it retired · what evidence showed it worked. Especially for familiar techniques ("use an append-only registry" is dry; "a cleanup heuristic destroyed a live worktree, so lifecycle state became an authoritative append-only record destructive ops must consult" is memorable + transferable).
10. **Conceptually nameable** — compresses to a memorable name carrying the mechanism (Read the Model Don't Copy It · One Door Enforced · Trust-Nothing Completion Gate · Closed Action Vocabulary · Preservation Invariant · Computed Control Blast Radius · Model-Derived Assurance Coverage). A mechanism nameable only by a long description of its current implementation may be an implementation detail.
11. **Expands the range of the book** — the printed catalogue should show breadth of what MAGE can govern: intent · architecture · behavior · mutation authority · validation · provenance · lifecycle · concurrency · deployment · observability · governance-of-governance. A mechanism can earn inclusion by demonstrating an important NEW CLASS of problem even if not foundational (Governance graph: once controls proliferate, the control system itself needs modeling — expands beyond "add more guardrails").
12. **It is awesome (legitimate)** — striking demonstrations of what becomes possible when an agent fleet can cheaply build+maintain engineering machinery (blast radius of an architectural migration across governance controls · test evidence ↔ modeled invariants · composed lifecycle machines with cross-machine property checks · test placement from journey criticality · document mutation history from embedded provenance · nested timeout-budget ordering · governance graph detecting control collisions). "Awesome" ≠ complicated — it means the entry makes the reader revise their estimate of what disciplined agentic engineering can look like.

**EXCLUSION criteria (reasons to demote to sidebar/example/known-use/online, NOT delete):**
1. **Merely an instance of a broader included pattern** (the biggest reason) — PdfModel/Office-models/canonical-walkers/Redis-seam/typed-service-client are all instances of "one sanctioned surface, enforced against bypass"; attribution-prefix/mutation-stamps/wiring-lint/derived-changelog are parts of a broader provenance pattern; model-query-CLI/codegen/registry/sync-declaration/parity-checks may be layers of the executable-model lifecycle. Don't present one intellectual move as five inventions.
2. **Standard practice with no important agentic transformation** — ordinary canary deploy · basic runbooks · standard fuzzing · normal property-based testing · conventional design-doc templates · generic resource semaphores. May belong in the narrative (you used them) but don't automatically deserve canonical status. Burden: *what does the agentic environment change about it?* If "we needed more of it," probably not a flagship.
3. **Solves a temporary limitation of current agent runtimes** — pre-compaction capture · periodic reminders · runtime-hook prompt injection · current-model role routing · one-vendor orchestration-API hacks. Document online as historically useful; little permanent print space unless generalized around a durable obligation.
4. **Primarily local infrastructure** — host mutexes · build-concurrency limits · test serializers · marker caches · cron alert gates · particular worktree-cleanup protocols · one exact merge-train batching algorithm. Test isn't difficulty/usefulness — it's whether it advances the reader's understanding of the METHODOLOGY. Some local mechanisms qualify when they reveal a deeper principle (agent registry → "authoritative lifecycle state before destructive action"; the marker-cache impl alone is too local).
5. **Lacks an interesting consequence** — all-upside is under-analyzed/trivial. If consequences amount to "improves consistency / agents find info more easily / process more reliable," it doesn't need several pages. Strong patterns have sharp tradeoffs / failure modes / applicability conditions / escape-hatch problems.
6. **Cannot be explained independently** — if it needs ten pages of DocAble architecture first, too embedded. A printed entry needs a recognizable recurring problem · a general mechanism · a concise diagram · a portable example. Highly entangled local machinery → online.
7. **Repeats a chapter without adding reference value** — must add a reusable pattern form / applicability guidance / consequences / variants / known-uses / related patterns. A template restatement of the chapter doesn't earn pages.
8. **Title exposes implementation residue, not the idea** — "Final-Opus trust-nothing re-run" · "three-stanza tree-SHA markers" · "N=1 flock on dotnet test" · "F10 mutator-stamp-wiring lint." Before excluding, TRY RENAMING/GENERALIZING ("Final-Opus trust-nothing re-run" → Re-Derived Definition of Done; "F10 mutator-stamp-wiring lint" → part of Complete Provenance Coverage; "sole raw-Redis seam" → One Door Enforced). Exclude only when no compelling general pattern remains.
9. **Novelty depends on the reader not knowing an established field** — model-driven engineering · formal methods · safety engineering · SRE · DevOps · distributed systems · testing research · provenance systems · event sourcing. An established technique can be included, but the novelty claim must be precise: novel agentic application · novel composition · changed economics · unusually complete enforcement · new role in MAGE. Be confident but not historically careless.
10. **Clever but distracts from the book** — e.g. merge-train MIS batching (construct a conflict graph, choose a pairwise non-conflicting batch — clever, but cleverness ≠ central). Ask: *does it make the reader understand MAGE better, or merely admire the implementation?* Admiration → online; print competes with the conceptual spine.

**RUBRIC (0/1/2 per dimension; diagnostic, not an automatic cutoff):**
Novelty · Agentic-significance · Durability · Generality · Thesis-relevance · Architectural-depth · Evidence · Tradeoffs · Compositional-value · Wow-factor.
- 16–20: almost certainly print · 12–15: print when it adds breadth or has a great story · 8–11: usually sidebar/example/online · <8: probably local documentation.

**OVERRIDES (stated, not hidden):** Foundational (needed to understand the method even if not novel) · Awesome (unusually innovative, broadens imagination) · Coverage (represents an important mechanism class otherwise absent) · Case (indispensable to understanding DocAble) · Historical (important field-report artifact even if transient).

**GOVERNING EDITORIAL PRINCIPLE:** the print catalogue holds three kinds — (1) **Foundational** patterns that define MAGE · (2) **Innovative** patterns that make the contribution distinctive · (3) **Showpiece** patterns that demonstrate how far the method can be taken. No target count — if 27 survive, print 27; don't include 60 weakly-differentiated entries nor cut excellent ones for a neat number. The right question for every entry: **does this give the reader a durable idea worth carrying into their next system?**

### Task 3 SUPPLEMENT — a three-level catalogue ARCHITECTURE (author follow-up)

Move from a flat list to THREE LEVELS:
- **Level 1 — Principles** (the few deep claims that EXPLAIN the catalogue; NOT pattern entries): bind intent to structured models · reconcile models with reality · constrain action through sanctioned surfaces · rederive evidence rather than trust reports · convert recurring failures into enforced mechanisms · preserve provenance + accountability · model the governance environment itself.
- **Level 2 — Canonical patterns** (reusable solutions; final set DISCOVERED not chosen — ~20/27/34): Executable Source of Truth · Drift/Parity Gate · Read the Model Don't Copy It · One Door Enforced · Closed Action Vocabulary · Re-Derived Definition of Done · Model-Derived Assurance Coverage · Preservation Invariant · Caused-By Provenance · Governance Graph.
- **Level 3 — Variants / components / known uses** (preserve the concrete material): PdfModel = known-use of One Door · raw-Redis seam = another · ServiceClient = typed distributed variant · N=1 test-lock + M=8 build-semaphore = cardinality variants of mediated resource admission · mutation-stamps + derived-changelog = components of Caused-By Provenance · pre-compaction capture = historically-contingent variant of context preservation.

**KEY DISTINCTION — FAMILY vs PATTERN vs INSTANCE.** For every entry ask: (a) a **family**? (broad territory, several distinct solutions — "Governed semantic boundaries" holds sole-mutation-surface / typed-cross-service-contracts / closed-action-vocabularies / mediator-coverage-lints — related, not identical); (b) a **canonical pattern**? (recurring problem · forces · reusable solution structure · consequences · a meaningful guarantee boundary — One Door Enforced); (c) an **instance / implementation technique**? (strong instance, no independent canonical status — PdfModel). This three-level classification solves most of the inflation problem.

**BEWARE FALSE MERGERS.** Do NOT merge because diagrams look similar. Blocking-semantic-lint / drift-parity-gate / provenance-coverage-lint / mediator-bypass-lint are all "lints" — but that's the enforcement TECHNOLOGY, not the pattern; they enforce DIFFERENT RELATIONS (implementation ⊨ semantic policy · model ⟷ reality · every mutation site → provenance · every call → authorized seam). "Use lints" destroys the content. Likewise never collapse all models into "executable model" — user-journey / SM-composition / timeout-ordering / synchronization / governance-graph express different SEMANTICS + support different reasoning. **The right abstraction preserves the RELATION being modeled/enforced, not the implementation mechanism.**

**PRACTICAL METHOD — card + cluster.** For each entry make a temporary card: **Failure class · Engineering obligation · Solution structure · Guarantee · Semantic level · Forces/tradeoffs · Dependencies · Known uses · Likely parent family.** Then CLUSTER: **merge** when the first SIX fields (failure/obligation/structure/guarantee/semantic-level/forces) are substantially the same and only KNOWN-USES differ; keep **separate** when the obligation OR guarantee differs even with the same implementation tech. (Principled clustering, not editorial instinct.)

**NAME AFTER ABSTRACTION.** Do NOT keep implementation-biased names while clustering (they hide commonality). Rename the abstraction FIRST, then sort items into components/variants/examples: {F10-mutator-stamp-wiring-lint · a11y_-prefix · per-mutator-stamps · derive-changelog} → **Complete Mutation Provenance**; {test-serializer · build-serializer · whole-sweep-mutex · resource-pressure-gating} → family **Mediated Resource Admission** — which may SPLIT into two patterns (fixed-capacity concurrency mediation vs. adaptive pressure-based admission+shedding — split by FORCES + GUARANTEES, not "both control compute").

**THE CLAIM TO MAKE:** not "we discovered 70 governance mechanisms" but *"the case produced ~70 concrete mechanisms; comparative analysis reduced them to a smaller set of recurring pattern families + canonical patterns, the remainder retained as variants and known uses."* (Doesn't mistake implementation count for conceptual contribution; aligns with the case-study method: incidents → mechanisms → compared → recurring structures become patterns.)

**WARNING — generalize the IDEA, not the EVIDENCE.** Local mechanisms are what make the book credible; a fully-generalized catalogue with no concrete machinery becomes the vague governance literature we dislike. Each CANONICAL PATTERN must retain: **one vivid failure · one concrete DocAble implementation · one diagram · one code/model fragment · ≥1 alternative implementation · clear limits.** THE TEST: after reworking a reader can say BOTH "I understand the general engineering move" AND "I can see exactly how Davis implemented it and why." Only the second → repo docs; only the first → abstraction vapor.

**GoF CONTRAST (state it; don't copy their ontology):** GoF catalogued reusable structures for collaborations INSIDE an OO program; this catalogue's subject moved — the mechanisms that organize the ENGINEERING ENVIRONMENT around an agent fleet (the representations it reasons through, the surfaces it acts through, the evidence its work must produce, the controls that decide what enters the product). **OPENING PASSAGE (author-drafted; use/adapt — self-communicate to voice):**
> **The Governed Engineering Environment** — The entries that follow are not seventy independent design patterns. They are the concrete machinery of a governed engineering environment: the models, sanctioned action surfaces, controls, evidence structures, and feedback loops through which an agent fleet performs engineering work.
> The main text developed two theses. The Modeling Thesis says agents work coherently when intent and system structure are bound into compact, structured representations they can reason through. The Alignment Thesis says implementation stays trustworthy when the environment mechanically holds it to those representations and the policies they express. The catalogue shows what those theses look like when built.
> Its entries do not all occupy the same level. Some are canonical mechanisms, such as an executable source of truth or a drift gate. Some are compositions, such as the provenance stack that joins a sanctioned mutation seam, attribution records, coverage checks, and a derived changelog. > The closest predecessor in form is Design Patterns, but the subject has moved. The Gang of Four catalogued recurring structures inside object-oriented programs. > Taken together, these mechanisms form a construction kit and reference architecture for the governed engineering environment. No system needs every entry. The catalogue supplies a repertoire from which an engineer chooses according to the failures, risks, and assurance obligations of the system at hand.

## TASK 4 — DURABILITY MODELING (obligation vs 2026-implementation) — **NEXT SESSION; author 260802: "do not act, surface a report for the next session."** Runs AFTER Phases 1–3 + the final deploy.

**The distinction to model.** Every mechanism / pattern / claim carries two separable things: (1) a **durable engineering OBLIGATION** — the general, permanent requirement it serves (e.g. "expose the relevant constraints at the point of action"; "establish completion by independently re-derived evidence"; "keep the map equal to the territory") — *canon-worthy*; and (2) a **2026 IMPLEMENTATION** of that obligation — the specific mechanism as built today (e.g. "pre-compact hooks that capture the right state"; context re-injection; model-tier routing on today's capability gaps) — *a time-stamped artifact*.

**Tag every 2026 implementation by change-likelihood:** **near-term-volatile** (likely to change as foundation models improve — pre-compact/context-loss compensations, reminders-for-forgetfulness, prompt-format tricks, token-boundary hacks, today's-tier routing) vs. **mid/long-term durable**.

**MODELING FIRST.** Capture the obligation↔implementation split + the volatility tag in a model (a new `durability` model, or fields on the claims/catalogue models) so we can QUERY the manuscript: **how much of the book is 2026-era vs. timeless?** Produce the durability REPORT — an inventory + % of durable-obligation content vs. 2026-implementation content, and within the latter the volatile-vs-durable split.

**WHY — the goal is to JOIN THE SE CANON.** A canon book foregrounds the DURABLE obligations (which outlast the current agent generation) and clearly marks the 2026-era implementations as dated artifacts, so they age gracefully rather than dragging the book down. Drives: (a) what PRINT leads with (durable obligations) vs. relegates/time-stamps (2026 implementations → online or explicitly marked); (b) the framing throughout ("the obligation survives even if this implementation changes"). Operationalizes Phase-3 rubric criterion 6 (durability) across the WHOLE book, not just the catalogue.

## PUNCH-LIST ITEM — the formal "MODEL" definition (author 260802; do IN this run, MODELS-FIRST) — **the most important + least-settled definition**

The book's intuitive definition — *"prose is too vague, code is too verbose, and a model occupies the useful middle"* — is memorable + pedagogically strong, but **not operationally sufficient**: the catalogue calls MANY things models (registries · graphs · manifests · state machines · tables · typed records · obligations · topology descriptions · provenance maps), risking "any useful structured representation." KEEP the intuition; ADD ONE FORMAL definition **early**:
> **Model.** A deliberately reduced, machine-readable representation of system intent, structure, behavior, policy, or evidence that supports reasoning, derivation, or checking, and whose relationship to the implemented or observed system is mechanically maintained.
