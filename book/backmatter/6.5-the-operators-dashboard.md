# The Operator's Dashboard

The book measures many numbers. Only some are numbers you *steer by*. A metric earns a place on this
dashboard when it meets one test: it is a useful agent-loop metric, or an org-level target for engineering
with MAGE — not merely a figure the case study reports. A diagnostic you read once to justify a choice, or
a payoff you measure but never drive toward a goal, stays in its chapter and off this page.

The [2.5](2.5-metrics.html) reference collects the *in-loop* governance metrics — the ones that drive a
single decision inside one commit or one run. This is the companion to it, one level up: the program-level
metrics that track the whole build across weeks. Read 2.5 to steer a loop iteration; read this to steer the
program.

[ref:operators-dashboard] gives each one — what it counts, the call it informs, the direction that means
health, and the chapter where it is defined.

Four metrics the book names are deliberately left off. Each is measured, none is steered by. **MBSE
navigation token-savings** ([3.1](3.1-the-executable-zoo.html)) is a model-payoff diagnostic — you read it
to justify the model, not to run the build. **Model-sync efficacy** ([3.8](3.8-keeping-models-in-sync.html))
is a gate you keep green, not a number you drive toward a target. **Grammar coverage** and **model-claim
coverage** ([4.6](4.6-generative-validation.html)) are technique-local oracles in the coverage family, local
to generative validation rather than targets for the whole program. The full set, with the inclusion verdict
and rationale for each, lives in the dashboard's model file.
