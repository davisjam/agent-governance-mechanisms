# What This Book Argues

This book makes a handful of central claims. The chapters ahead defend them; this page only names them, so you can watch each one being tested as you read.

1. **Cheap code, costly judgment.** Coding agents have made writing code fast and cheap. Once implementation stops being the bottleneck, the scarce and expensive work moves up a level — to judgment, architecture, validation, and governing what the agents produce. The engineer's leverage is no longer in the typing.
2. **Large software engineering is a reasoning problem, not merely a coding problem.** A big system eventually grows too complicated for anyone, person or AI, to hold in mind at once. The hard part of building it is holding coherent reasoning over the whole as it changes, not producing the next function. That, not raw implementation speed, limits how large a system a fleet of agents can build.
3. **Models are valuable because they help humans and AI reason about large systems.** Explicit models earn their place by letting people and agents reason about a system without holding all of its code in mind at once. A model is not documentation pinned beside the code; it is the thing you think through. The book calls this the Modeling Thesis.
4. **Reliability should come from the engineering environment, not from repeated human inspection.** Software should not be trustworthy only because people keep making the right call and catching mistakes by hand. Reliability should come from the environment itself — the constraints, sensors, validators, and gates that hold every change to the standard automatically. The book calls this the Alignment Thesis.
5. **Every recurring failure should become permanent engineering infrastructure.** When a mistake reveals a recurring or consequential failure class, the answer is not to resolve to be more careful. Build something that makes the mistake impossible, or that catches it every time, so the lesson is captured once and never relearned. Each such conversion is engineering capital: it lowers the future cost of change, so effort compounds instead of being spent twice on the same problem, for as long as the capital stays fit.
6. **The engineer's job changes.** Less time writing implementation; more on the shape of the system, the models everyone reasons through, checking the work, and governing the fleet that produces it.

The rest of the book exists to earn these.
