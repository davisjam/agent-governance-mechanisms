# What This Book Argues

This book makes a handful of central claims. The chapters ahead defend them; this page only names them, so that as you read you can watch each one being tested. Read it as the opening of an argument, not its conclusion.

1. **Cheap code, costly judgment.** Coding agents have made writing code fast and cheap. Once implementation stops being the bottleneck, the scarce and expensive work moves up a level — to judgment, architecture, validation, and governing what the agents produce. The engineer's leverage is no longer in the typing.
2. **Large software engineering is a reasoning problem, not merely a coding problem.** A big system eventually grows too complicated for anyone, person or AI, to keep entirely in mind at once. The hard part of building it is holding coherent reasoning over the whole as it changes, not producing the next function. That, and not raw implementation speed, is what limits how large a system a team or a fleet of agents can build.
3. **Models are valuable because they help humans and AI reason about large systems.** Explicit models earn their place by letting people and agents reason about a system without holding all of its code in mind at once. A model is not documentation pinned beside the code; it is the thing you think through. The book calls this the Modeling Thesis.
4. **Reliability should come from the engineering environment, not from repeated human inspection.** Software should not be trustworthy only because people keep making the right call and keep catching each other's mistakes by hand. Reliability should come from the environment itself — the constraints, sensors, validators, and gates that hold every change to the standard automatically. The book calls this the Alignment Thesis.
5. **Every recurring failure should become permanent engineering infrastructure.** When the same mistake happens a second time, the answer is not to resolve to be more careful. The answer is to build something that makes the mistake impossible, or that catches it every time, so the lesson is captured in the environment once and never has to be learned again.
6. **The engineer's job changes.** The engineer spends less time writing implementation and more time deciding the shape of the system, building the models everyone reasons through, checking that the work is right, and governing the fleet that produces it. Architecture, modeling, validation, and governance become the work.

The rest of the book exists to earn these.
